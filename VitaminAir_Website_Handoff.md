## 1. What VitaminAir is becoming

We want to rewild land in Cambodia and, over time, build a sustainable living village. The website should make that direction clear without making the village sound finished or the restoration plans sound funded already.

The story should progress naturally:

1. We bought land and are allowing much of it to recover naturally.
2. Some areas were cleared decades ago. We want to trial native tree planting on selected parts of those areas.
3. We want to record what works and create an example others can learn from.
4. Over time, we hope to build a village where people can live closer to nature while staying connected to their work and the world.

Our existing content includes learning, leadership and community themes. Preserve those in the journal. The main website should now lead with the land, forest recovery and future living vision.

The audience includes people curious about the project, potential planting and research collaborators, supporters, and people interested in the longer-term village. Give each a simple way to understand the project and contact us.

## 4. Visual direction

Aim for a small, thoughtful environmental venture with a startup mindset. It should feel grounded in the land and approachable to people who want to help build something over time.

Prefer warm off-white, a distinctive forest green, dark readable text and a restrained earth-colour accent. Use one or two fonts. A little character in headings is welcome if the body remains easy to read. Establish VitaminAir's own palette and details rather than copying SmallWorld's branding.

Use a clear reading column, generous but sensible spacing, fine separators and simple text-led sections. A small number of genuine photographs can carry more meaning than large grids of generic cards. Use simple expandable rows only where they help organise secondary information. Keep the core story visible.

Avoid an oversized navigation menu, constant rounded cards, noisy gradients, floating decorative blobs, carousels, animated statistics, heavy scroll effects and full-screen background video. Keep motion minimal and respect reduced-motion settings.

The technology identity should come through in clarity, practical thinking and how we document our work. We do not need a futuristic dashboard or speculative technology products to express it.

## 7. Implementation after design selection

First inspect the working repository and any `AGENTS.md` instructions. Preserve unrelated work and existing useful assets. If no frontend exists, set up a small Vite + TypeScript project. Use local content and a small typed configuration file. For example:

```text
src/content/pages/       Main page copy in Markdown
src/content/journal/     Public articles in Markdown

src/data/site.ts         Navigation, contact, map and project facts
public/images/           Local, optimised image assets
source-archive/          Original supplied Markdown files
CONTENT_GUIDE.md         How to edit and publish content
```

Adapt this layout to the actual repository if necessary. Keep facts in one place so changing a pilot status or land figure does not require editing multiple components. Components should handle presentation; content files should hold prose.

Define a simple documented front-matter format for articles: title, date, description, tags, optional image and alt text, optional verified author, content type, publication status, canonical path and any archive note. Publication status and article type should be separate: a published story can still be labelled a story. Use plain Markdown rather than requiring JSX to write a post.

### Markdown rendering for blogs and updates — required

Implement an actual **Markdown renderer**, with the same reading layout for blog posts and project updates. Discover `.md` files automatically from the content folder, parse their front matter, and render their bodies as properly styled HTML. Do not hardcode articles in React components or require a manually maintained post registry.

Support headings, paragraphs, lists, links, images with alt text, blockquotes, horizontal rules, fenced code blocks and tables. Keep front matter out of the visible article. The article layout should show its title, date and relevant status/type labels, with readable spacing on phones and desktop.

The publishing workflow must be:

1. Create an `.md` file in `src/content/journal/`, or copy an existing post template.
2. Fill in its metadata and write the update in ordinary Markdown.
3. Preview it locally, then mark it `published` when ready.
4. Rebuild and upload the static output. The post gets its own page and appears automatically in the journal, sorted by date.

For new posts, derive the URL from the filename unless an explicit canonical path is supplied. Preserve the existing paths for migrated articles. Drafts must remain outside the public output, journal listing and sitemap, including drafts placed in the journal folder. Editing a post must not require changing application code. Any homepage section showing the latest posts should use the same generated content index; curated selections can use a simple metadata flag.

Provide a copyable post template, for example:

```markdown

title: "Planning our first planting trial"
```

This is an example template, not an additional published project update. Demonstrate during handover that adding a Markdown file creates a rendered article and updates the journal without editing a component. Keep this workflow local and static; it does not require a CMS or backend.

Keep public page URLs stable. Produce static, readable HTML for core pages and article routes at build time, with useful titles, descriptions and social metadata. Any build-time generation must run locally or in the build pipeline; serving the site must not require a backend. Document the static hosting and deep-link behaviour.

There is no need for accounts, a database, an admin dashboard, a CMS, booking, payments, newsletter infrastructure or a new API. A local Markdown workflow is enough for now. Keep dependencies few and explain any substantial addition.

Use semantic HTML, readable contrast, keyboard-accessible navigation, visible focus states and properly labelled controls. The mobile layout should be as clear as the desktop layout. Optimise images and fonts, reserve image dimensions and avoid unnecessary JavaScript.
